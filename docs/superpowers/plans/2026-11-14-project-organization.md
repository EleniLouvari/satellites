## Target structure

### Backend: `src/parcel_app/`

Three kinds of folders:

- `core/`, `auth/`, `jobs/`: infrastructure, used by everything.
- `sources/<provider>/`: everything specific to one data provider (accounts, connection test, remote job cleanup,
  provider defaults). This mirrors `data_preparation/sources/`.
- `pipelines/<pipeline>/`: one folder per analysis the app runs (routes, config, tasks).

```text
src/parcel_app/
  app.py                  FastAPI factory; routers come from the registry
  manage.py               migrate / set-password CLI
  settings.py
  core/                   infrastructure, no feature logic
    db.py
    security.py
    storage.py            contained(), checksum(), sanitize_text() (taken from artifacts.py)
  auth/
    routes.py             (from auth.py)
  jobs/                   generic background-job engine
    queue.py              enqueue / claim / reconcile (enqueue moves out of uploads.py)
    registry.py           NEW: job kind -> handler, lane, error message, interrupt hook; router list
    worker.py
    process_control.py
    windows_job.py
    progress.py
  sources/                data providers
    openeo/
      accounts.py         Copernicus account routes (from accounts.py)
      tasks.py            test_account job (from tasks._test_account)
      remote_cleanup.py   delete remote openEO jobs (from remote_cleanup.py + the openEO part of deletion.py)
      defaults.py         Sentinel/openEO form defaults (from config.py)
    (later: hub/, planet/)
  pipelines/
    uploads/              routes.py, inspection.py, tasks.py (inspect)
    parcel_stats/         routes.py (runs.py), config.py, tasks.py (validate/run/resume/bundle),
                          files.py, artifacts.py, completion.py, deletion.py
    eda/                  routes.py (eda_api.py), config.py (eda_config.py), tasks.py (eda_task.py)
    (later: ml/)
  migrations/
    001_core.sql          users, sessions, EO accounts, uploads, runs, jobs (current schema.sql content, unchanged)
    002_eda.sql           eda_runs
```

**Registry.** Each `sources/*` and `pipelines/*` package declares its job kinds and router in its `__init__.py`, for example:

```python
# parcel_app/pipelines/eda/__init__.py
JOBS = {"eda": JobSpec(handler="parcel_app.pipelines.eda.tasks:execute_eda", lane="run",
                       error="Error: EDA failed; ...", on_interrupt=mark_eda_interrupted)}
ROUTER = "parcel_app.pipelines.eda.routes:router"
```

`jobs/registry.py` lists the enabled packages; `worker.py`, `tasks.py` and `app.py` read from it instead of hard-coding
kinds. Behaviour stays the same: same job kinds, same lanes, same SQL. Adding HUB, Planet or ML later means one new
folder plus one line in the registry.

**What this plan does *not* do for providers:** it does not add a provider interface, a `provider` column or a provider
choice in the form. Today there is only openEO, so an interface would be guesswork. Those changes belong to the plan that
adds the second provider; this plan only makes sure the openEO code is in one place so it is clear what that interface has to cover.

`manage.py migrate` runs `migrations/*.sql` in name order. Every statement is already idempotent
(`CREATE ... IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`), so existing databases are unaffected.

## Risks

- **Running workers**: job rows store only `kind` names, not module paths, so queued jobs survive. Stop the worker before deploying anyway.
- **Child processes**: worker children import task modules by their new paths; covered by `test_worker.py` and the smoke test.
- **Saved run configurations** store processing options and paths, not Python module paths, so they are unaffected.
